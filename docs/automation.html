Rules and Passive Scan

Two things that work on traffic without you watching: one rewrites, one reads.

Match and replace

Regex rules over the request line, the status line, headers or bodies, in either direction. The tester shows what a rule does to a sample before you arm it, which is where a greedy pattern should be caught.

A few that earn their place on most engagements:

GoalMatchReplace with
Pin a session for the whole test ^Cookie: .*$ Cookie: session=PINNED_VALUE
Strip a cache buster [?&]_=\d{10,13} (empty)
Force a role in a JSON body "role"\s*:\s*"[^"]*" "role": "admin"
Expose a hidden field type=(["']?)hidden\1 type=text
Drop a blocking security header ^Content-Security-Policy:.*$ (empty)
Unmask a server version for a note ^Server:\s*(.+)$ Server: $1 [seen]

A response rule changes what you see, not what the target sent. History keeps the original alongside the rewritten version, so a screenshot taken after a rule fired is still traceable to the real bytes.

Passive scan

Built-in rules read traffic that has already been captured and flag what deserves a second look. Findings appear with the flow they came from. The scanner sends nothing of its own, so it cannot touch the target, trip a rate limit, or change the result of whatever else you are running. It also runs only when you press Scan: a scan reads the body of every captured flow, so it waits to be asked, and a second one reads only what has arrived since.

By default it reads the places secrets actually live, source and text assets and JSON APIs, rather than every image and font. The scope list is editable in the app, and * means everything. In scope only is on by default as well, so the scan stays on the hosts in the project Scope; with no Scope set, everything is in scope and nothing is skipped.

Adding your own detector

The built-in detectors are a plain list in the repo. There are 48 of them, and adding the 49th is copying a line:

FileHolds
src/lib/passive-rules.js BUILTIN_RULES: every detector the app ships, as one array.
src-tauri/src/mcp.rs The Rust mirror used by the MCP scanner. Keep the two in step when you add a rule.
src/lib/passive.js How a rule is run, and the default scope of file types it reads.

The shape of a rule, and three of the ones that ship:

{ id: 'jwt', title: 'JSON Web Token', severity: 'medium',
  pattern: '\\beyJ[A-Za-z0-9_-]{8,}\\.[A-Za-z0-9_-]{8,}\\.[A-Za-z0-9_-]{4,}', flags: 'g' }

{ id: 'aws-key', title: 'AWS access key ID', severity: 'high',
  pattern: '\\b(?:AKIA|ASIA)[0-9A-Z]{16}\\b', flags: 'g' }

{ id: 'private-key', title: 'Private key block', severity: 'high',
  pattern: '-----BEGIN (?:RSA |EC |OPENSSH |DSA |PGP )?PRIVATE KEY-----', flags: 'g' }

id is the key findings are grouped by, severity is one of high, medium, low or info, pattern is a regex written as a string, so backslashes are doubled, flags adds to the g that is always applied, and an optional group reports one capture group instead of the whole match, which is how the hardcoded-secret rule reports the value and not the keyword in front of it.

Three worth adding for a local stack, as a starting point:

{ id: 'internal-host', title: 'Internal hostname', severity: 'low',
  pattern: '\\b[a-z0-9-]+\\.(?:internal|corp|lan|intranet)\\b', flags: 'gi' }

{ id: 'idn-phone', title: 'Indonesian mobile number', severity: 'low',
  pattern: '\\b(?:\\+62|62|0)8[1-9][0-9]{6,10}\\b', flags: 'g' }

{ id: 'debug-flag', title: 'Debug flag enabled', severity: 'medium', group: 1, flags: 'gi',
  pattern: '\\b(debug|verbose|test[_-]?mode)\\b\\s*[:=]\\s*(?:true|1|"on")' }

The same shape is accepted by the custom-rule editor in the app, so you can try a pattern at runtime first and only move it into the file once it holds up. The Rust side has no lookaround, so a rule that needs lookbehind is matched broadly there and refined in code: check an existing rule before you rely on one.
