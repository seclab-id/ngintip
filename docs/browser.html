Built-in browser

It uses the browser already on your computer. Nothing is bundled, and nothing is downloaded unless you have none.

Open browser

Setting a proxy by hand, trusting a CA, then remembering to undo both is the dull part of starting. Ngintip launches a Chromium you already have with the proxy set and a profile of its own, so your everyday browser, its logins and its extensions are left alone.

On first use it looks through the standard install locations for your platform and takes the first one that exists. Chrome, Chromium, Edge and Brave all qualify: they are the same engine, and the proxy flags are identical.

Where it looks

PlatformChecked, in this order
macOS /Applications/Google Chrome.app, the same under your home folder, /Applications/Chromium.app, Google Chrome for Testing.app, Microsoft Edge.app, Brave Browser.app
Windows %ProgramFiles%\Google\Chrome\Application\chrome.exe, the same under %ProgramFiles(x86)% and %LOCALAPPDATA%, then %ProgramFiles%\Microsoft\Edge\Application\msedge.exe and its x86 twin
Linux /usr/bin/google-chrome, google-chrome-stable, chromium, chromium-browser, /snap/bin/chromium, microsoft-edge, brave-browser

Settings shows what it found, as a full path, so you always know which binary will start. If the list misses yours, set the path yourself: that is the next section, and on a locked-down or unusual machine it is the part that matters.

Setting the path by hand

Settings has a Browser path field. Put an absolute path to the executable in it and press Save. There is an Extra flags field beside it for anything a target needs, for example --incognito or --lang=en.

macOS

You can give it either the bundle or the binary inside it. A path ending in .app is resolved to Contents/MacOS/<name> for you, which is why dragging an app into the field works. 

/Applications/Brave Browser.app
/Applications/Brave Browser.app/Contents/MacOS/Brave Browser
/Users/you/Applications/Chromium.app

Finding the binary of any installed app: right-click it in Finder, Show Package Contents, then Contents/MacOS. The file with no extension is the one.

Windows

Give the full path to the .exe. No quotes are needed even when the path has spaces, because the field is a path and not a command line. 

C:\Program Files\Google\Chrome\Application\chrome.exe
C:\Users\you\AppData\Local\Chromium\Application\chrome.exe
C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe

To find it: right-click the shortcut, Properties, and read the Target field. Or run where chrome in a terminal.

Linux

Point it at the real executable, not a desktop entry.

/usr/bin/chromium
/usr/bin/google-chrome-stable
/snap/bin/chromium
/opt/brave.com/brave/brave

which chromium or readlink -f $(which google-chrome) will tell you. A Flatpak browser is not a plain binary: it runs through flatpak run, so point the field at a small wrapper script that passes its arguments on, and mark the script executable.

If you have none

Only then does it offer a download: Chrome for Testing, Google's plain .zip build made for automation. It is unpacked with the system's own tool, ditto, unzip or Expand-Archive, so app bundles, symlinks and executable bits survive. Builds exist for macOS on Apple Silicon and Intel, Linux x86-64 and Windows x64.

Profiles

Every launched browser gets its own --user-data-dir, which keeps its cookies, history and extensions away from your daily profile. There are two kinds, and the difference matters on a long engagement.

KindLivesUse it for
Throwaway A temporary directory, scoped to this app instance, swept when you quit. The default. A clean browser every time, nothing left behind.
Saved with the project ngintip_browser/<project>_default/, next to your .ngintip file. Staying logged in between sessions, so day three does not start at the login page.

The switch is in Settings: Save browser profile (cookies and history) with this project. Because the directory sits next to the project file, moving the project moves the session with it.

Several browsers at once

Turn on Multiple profiles and you can name as many as you need, then spawn each one separately. Each gets its own directory, <project>_<name>, so they share nothing: separate cookies, separate storage, separate sessions.

That is the setup for the test nobody enjoys doing by hand: admin in one window, a normal user in the second, an unauthenticated visitor in the third, all three recorded into the same capture at the same time. Take the admin's request, replay it as the user, and the two sessions never contaminate each other because they were never in the same profile.

Chrome locks a profile directory, so two browsers cannot share one. That is why each profile is its own directory, and why a throwaway profile is scoped to the running instance: two copies of Ngintip never sweep each other's browsers.

Remote debugging

A profile can also expose the Chrome DevTools Protocol, bound to 127.0.0.1 on a port you choose. It is opt-in per project and off otherwise, for when you want to drive the browser from a script while its traffic is being recorded.

Closing Ngintip closes the browsers it started, including their helper processes, rather than leaving one running with a proxy set.

Certificate errors are ignored inside that profile, which is what lets you read HTTPS without installing the CA first. It is the same flag browser automation uses, and it applies only to the throwaway profile Ngintip launched, never to your own browser.
