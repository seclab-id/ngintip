Performance

Numbers from one real engagement: what the capture costs on disk, and what the app costs in memory and CPU with that capture open. Aggregates only: no host, no path and no payload from it appears on this site.

One file, a quarter of the size

The capture is compressed on save and streamed back on open, so the project you hand over is a fraction of the database inside it. Nothing is pruned to get there: every request, answer, header and body is still in the file.

Database 1.55 GB
Saved file 412.6 MB

3.8x smaller, or 74% of the bytes gone, with nothing dropped from the capture.

Where the bytes go

Inside the uncompressed database the split is not where most people guess:

66.8% 32.9%
  • Search index 1,058 MB
  • Flows: headers, bodies, metadata 520 MB
  • Settings, Repeater history, logs 4.6 MB

Two thirds of the database is the full-text index, not the traffic. That is what makes a search across 41,692 decoded bodies answer in half a second instead of walking the table, and it is derived data: it compresses hard, which is most of why the saved file is a quarter of the size.

What it costs while it is open

Everything above was read off the file. The rest of this page is the running app with that same project open: Ngintip 0.4.0, the installed build, on a ten core Apple M5 with 16 GB of memory and macOS 26.4, sitting on History with the proxy listener off. Memory is the figure Activity Monitor shows, and each CPU figure is process CPU time over a measured wall clock window rather than whatever instant a sampler happened to land on.

155 MBmemory, idle, everything
0.07%of one core, idle
0.3 msto open one flow

A 1.55 GB database and a sixth of a gigabyte of memory: the capture is not in RAM, and never was. Each flow goes from the proxy down a channel to a single writer thread and into SQLite, then it is dropped; the window asks for the rows it is actually showing and caches a few dozen. So this is a figure for the app, not a figure for the project, and it hardly moves as a capture grows.

Window 91 MB
Core 39 MB
GPU 17 MB
Networking 7.5 MB

155 MB in total, idle. Three of those four processes are the system webview drawing the window; the core is the part Ngintip ships, and it is the smallest of them.

Idle really is idle. Over a minute, the four processes together used 0.07% of one core, which on a ten core machine is seven thousandths of one percent of it. Nothing is polling: every poll in the window is gated on there being something to poll for, a browser it launched still running, or the Extensions or Settings view actually open, and is paused on top of that while the window is hidden. Sitting on History with a capture loaded starts no timer at all.

Under an agent reading hard

The other end of the range is an agent on the MCP server with no pauses in it: twenty four seconds of back to back queries, several hundred of them, pages of History, full text searches, filters and flow reads. The core ran at 89% of one core and its memory climbed from 41 MB to 275 MB, then fell back to 41 MB within a minute of the queries stopping. That rise is SQLite's page cache over a 1.55 GB file doing exactly what a cache is for, and it is returned.

The window used no measurable CPU at all during that, and its memory did not move. Nothing an agent asks for is routed through the UI, so a long agent session does not fight the operator for the window.

How long each thing takes

On the same 41,692 flow project, measured over the MCP server so the figures include encoding the reply:

Query time on a project of 41,692 flows
Open one flow, request and responsehistory_get0.3 ms
One flow's headers alonehistory_get, part=headers0.4 ms
A 50 row page of Historyhistory_list190 ms
A 50 row page from the oldest end of the capture155 ms
Filter by method, by status, or by a substring of the URL75 to 160 ms
Full text search across every decoded bodyhistory_search440 to 780 ms

Two of those rows matter more than their numbers. A page from the far end of a 41,692 row capture costs what the first page costs, because paging is done with a cursor and not an offset; an offset would make the last page the slowest, and over a capture that is still growing it would also silently skip rows. And a search costs the same whatever it finds: the term json matched 36,041 of the 41,692 flows and answered in half a second, a term present in none of them took the same half second, and asking for 100 hits instead of 20 cost nothing extra. The work is the index lookup, not the size of the answer.

Not measured here: what capture itself costs per request, which needs live traffic running through the listener. These numbers come from a finished engagement, and the honest way to get that one is a project of its own rather than writing test requests into somebody's real capture.

What the file actually is

A project is a SQLite 3 database, compressed, behind a seven byte header. Nothing exotic: if you want to read a capture with your own tools, you decompress it and open it with any SQLite client. 

4e 47 4e 54 50 43   "NGNTPC"   brand magic
02                  version    2 = zstd, 1 = gzip (older saves, still read)
28 b5 2f fd ...     zstd frame containing the SQLite database

A plain SQLite format 3 file with no header at all still opens, so an old uncompressed project is never stranded. The tables inside are the ones you would expect: flows, ws_messages, settings, repeater_history, intruder_results, logs, plus the FTS5 index that makes search instant.

How saving works

The app never edits the document in place. It works on a live, uncompressed SQLite file in its data directory, which is what makes writes durable while you capture, and Save streams that file through a zstd encoder straight into the document. Streaming is the part that matters at this size: a 1.55 GB database is never held in memory to be saved.

The level is zstd 12, with long distance matching turned on. That setting is deliberate: high enough to comfortably beat gzip's ratio, low enough that multithreaded compression still finishes faster than the old gzip save, and long distance matching is what catches the repeats across flows, since the same framework headers and the same JSON keys appear in thousands of messages.

Opening reverses it, decompressing as a stream so a large project does not have to fit in RAM twice.

And the app itself

The installer is 5.2 MB on Windows, 6.9 MB on Debian and Fedora, and 12.7 MB on macOS for a universal build carrying both architectures; installed, the macOS bundle is 28 MB. No bundled browser, no runtime to install first, no service left running: the proxy is Rust, and the window is the webview your system already has.
